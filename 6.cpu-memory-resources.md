# 🧩 Problem Statement (Adjust Pod Resource Requests)

<details>
<summary>Click to expand the problem statement</summary>

A wordpress application is running in the cluster but some pods fail to start due to overly high resource requests.

Your task is to:

1. Connect to the **correct host**
2. Identify the failing pods due to high resource requests
3. Adjust resource requests so all pods can be scheduled
4. Verify all pods are running and ready

```
[candidate@base]$ ssh <hostname>
```

### 📋 Configure the following:

In the **`app-workload`** namespace, the wordpress application includes a Deployment with **3 replicas**. Adjust the resource requests for all pods as follows:

1. Distribute node resources evenly among the **3 replicas**
2. Allocate fair CPU and memory shares to each pod
3. Add sufficient overhead to keep the node stable
4. Use **identical resource requests** for both containers and init containers
5. Do **not** change any resource limits

> 💡 Temporarily scaling the Deployment to `0` replicas may help when updating resource requests.

After the update confirm:
- The **`wordpress`** Deployment maintains **3 replicas**
- All pods are **running and ready**

</details>

### 📥 Script : setup_q06_resources.sh

```bash
#!/bin/bash
# ============================================================
# CKA Practice | Q06: Adjust Pod Resource Requests
# setup_q06_resources.sh
# Creates namespace and wordpress deployment with overly high
# resource requests causing pods to be in Pending state
# Re-run safe: only resets candidate work on subsequent runs
# Run on: controlplane node
# ============================================================

set -euo pipefail

NAMESPACE="app-workload"
DEPLOYMENT="wordpress"

echo ""
echo "==========================================="
echo " CKA Q06 — Setting up Resource Requests scenario..."
echo "==========================================="
echo ""

# ── Step 1: Reset candidate work ─────────────────────────────
echo "[1/3] Resetting candidate work from previous attempt..."

if kubectl get deployment "$DEPLOYMENT" -n "$NAMESPACE" &>/dev/null; then
    RUNNING_PODS=$(kubectl get pods -n "$NAMESPACE" \
        --field-selector=status.phase=Running \
        --no-headers 2>/dev/null | wc -l || echo "0")

    if [ "$RUNNING_PODS" -gt 0 ]; then
        echo "  Candidate fix detected ($RUNNING_PODS running pods) — restoring to original state..."
        kubectl replace --force -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: $DEPLOYMENT
  namespace: $NAMESPACE
spec:
  replicas: 3
  selector:
    matchLabels:
      app: wordpress
  template:
    metadata:
      labels:
        app: wordpress
    spec:
      initContainers:
      - name: init-container
        image: busybox:1.36.1
        command:
        - sh
        - -c
        - echo "Initializing..." && sleep 10
        resources:
          limits:
            cpu: "2500m"
            memory: "2600Mi"
          requests:
            cpu: "2400m"
            memory: "2500Mi"
      containers:
      - name: wordpress-container
        image: busybox:1.36.1
        command:
        - sh
        - -c
        - echo "Main container is running!" && tail -f /dev/null
        resources:
          limits:
            cpu: "2500m"
            memory: "2600Mi"
          requests:
            cpu: "2400m"
            memory: "2500Mi"
EOF
        echo "  Deployment restored to original state (high resource requests)."
    else
        echo "  No candidate changes detected — skipping restore."
    fi
else
    echo "  Deployment not found — will create fresh."
fi

echo "  Candidate work cleared."

# ── Step 2: Create namespace if not present ───────────────────
echo "[2/3] Checking namespace '$NAMESPACE'..."
if kubectl get namespace "$NAMESPACE" &>/dev/null; then
    echo "  Namespace already exists — skipping."
else
    kubectl create namespace "$NAMESPACE"
    echo "  Namespace created."
fi

# ── Step 3: Create deployment if not present ──────────────────
echo "[3/3] Checking deployment '$DEPLOYMENT'..."
if kubectl get deployment "$DEPLOYMENT" -n "$NAMESPACE" &>/dev/null; then
    echo "  Deployment already exists — skipping."
else
    echo "  Creating deployment '$DEPLOYMENT' with overly high resource requests..."
    kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: $DEPLOYMENT
  namespace: $NAMESPACE
spec:
  replicas: 3
  selector:
    matchLabels:
      app: wordpress
  template:
    metadata:
      labels:
        app: wordpress
    spec:
      initContainers:
      - name: init-container
        image: busybox:1.36.1
        command:
        - sh
        - -c
        - echo "Initializing..." && sleep 10
        resources:
          limits:
            cpu: "2500m"
            memory: "2600Mi"
          requests:
            cpu: "2400m"
            memory: "2500Mi"
      containers:
      - name: wordpress-container
        image: busybox:1.36.1
        command:
        - sh
        - -c
        - echo "Main container is running!" && tail -f /dev/null
        resources:
          limits:
            cpu: "2500m"
            memory: "2600Mi"
          requests:
            cpu: "2400m"
            memory: "2500Mi"
EOF
    echo "  Deployment created."
fi

echo ""
echo "  Waiting 10 seconds for pods to attempt scheduling..."
sleep 10
echo ""
kubectl get deployment "$DEPLOYMENT" -n "$NAMESPACE"
echo ""
kubectl get pods -n "$NAMESPACE"
echo ""
echo "✅ Practice scenario is ready!"
echo ""
echo "   Pods are in Pending state due to overly high resource requests."
echo "   Your task: adjust resource requests so all 3 pods can run."
echo "   💪 Go fix the resource requests!"
echo ""
```

# ✅ Solution

<details>
<summary>Click to expand the solution</summary>

### Step 1: Verify pods are Pending

```bash
kubectl get pods -n app-workload
```

Expected output — pods stuck in `Pending`:

```
NAME                         READY   STATUS    RESTARTS   AGE
wordpress-xxx-xxxxx          0/1     Pending   0          30s
wordpress-xxx-xxxxx          0/1     Pending   0          30s
wordpress-xxx-xxxxx          0/1     Pending   0          30s
```

---

### Step 2: Check why pods are Pending

```bash
kubectl describe pod -n app-workload | grep -A5 "Events:"
```

Expected output:

```
Warning  FailedScheduling  0/2 nodes are available: insufficient cpu, insufficient memory
```

This confirms pods cannot be scheduled due to high resource requests.

---

### Step 3: Scale the Deployment to 0 replicas

```bash
kubectl -n app-workload scale deployment wordpress --replicas=0
```

Verify:

```bash
kubectl -n app-workload get deployment wordpress
```

Expected output:

```
NAME        READY   UP-TO-DATE   AVAILABLE   AGE
wordpress   0/0     0            0           5m
```

---

### Step 4: Check actual node capacity and current resource usage

**First — get the actual total capacity of the node:**

```bash
kubectl describe node node01 | grep -A6 "Capacity:"
```

Expected output:

```
Capacity:
  cpu:     2
  memory:  3936496Ki
```

**Second — check what is already requested by existing pods:**

```bash
kubectl describe node node01 | grep -A6 "Allocated resources:"
```

Expected output:

```
Allocated resources:
  Resource    Requests      Limits
  --------    --------      ------
  cpu         100m (10%)    1 (100%)
  memory      10Mi (0%)     1Gi (56%)
```

> ⚠️ **Important:** Only look at the **Requests column** — NOT the Limits column.
> Kubernetes schedules pods based on Requests only. Limits can exceed 100% (overcommit) and are irrelevant for scheduling.

---

### Step 5: Calculate appropriate resource requests

Use the **Requests column** and **Capacity** values only:

**CPU:**
```bash
# Total CPU capacity = 2 cores = 2000m
# Already requested  = 100m
# Available          = 2000 - 100 = 1900m

echo "2000 - 100" | bc
# Output: 1900m available
```

**Memory:**
```bash
# Convert total memory from Ki to Mi
echo "scale=0; 3936496 / 1024" | bc
# Output: 3844Mi  ← total node memory

# Already requested = 10Mi
# Available         = 3844 - 10 = 3834Mi

echo "3844 - 10" | bc
# Output: 3834Mi available
```

**Distribute across 3 replicas × 2 containers = 6 containers total:**

```bash
# CPU per container
echo "scale=0; 1900 / 6" | bc
# Output: 316m  → use 200m (leave overhead for OS and kubelet)

# Memory per container
echo "scale=0; 3834 / 6" | bc
# Output: 639Mi  → use 400Mi (leave overhead for OS and kubelet)
```

> 💡 **Why use less than calculated maximum?**
> The OS, kubelet, and kube-proxy also consume CPU and memory on the node.
> Always leave some overhead — use **60-70% of calculated value** to keep the node stable.

**Final values to use:**

```yaml
requests:
  cpu: "200m"
  memory: "400Mi"
```

> ✅ **Sanity check before applying:**
> ```bash
> echo "6 * 200" | bc   # → 1200m  less than 1900m available? ✅
> echo "6 * 400" | bc   # → 2400Mi less than 3834Mi available? ✅
> ```

---

### Step 6: Edit the Deployment resource requests

```bash
kubectl -n app-workload edit deployment wordpress
```

> 💡 In vim run `:set paste` first to avoid formatting issues when editing YAML.

Update **both** the `initContainers` and `containers` `requests` sections — keep `limits` unchanged:

```yaml
spec:
  template:
    spec:
      initContainers:
      - name: init-container
        resources:
          limits:               # Do NOT change
            cpu: "2500m"
            memory: "2600Mi"
          requests:             # Update these values
            cpu: "200m"
            memory: "400Mi"
      containers:
      - name: wordpress-container
        resources:
          limits:               # Do NOT change
            cpu: "2500m"
            memory: "2600Mi"
          requests:             # Update these — must match init container
            cpu: "200m"
            memory: "400Mi"
```

Save and exit.

---

### Step 7: Scale the Deployment back to 3 replicas

```bash
kubectl -n app-workload scale deployment wordpress --replicas=3
```

NAME                    READY   STATUS    RESTARTS   AGE

All 3 replicas running and ready. ✅
